# 幽幽子挑战测试反馈核验

核验日期：2026-09-13。当前分支 `feat/yuyuko-trial-coop`，HEAD `71edf6e`。本轮仅核对朋友提供的日志、当前代码与已有逆向材料，未开展新的游戏实测，也未修改运行逻辑。

## 后续复现与修复

用户随后在本机双端复现：给顾客上菜并保留其待结账，通过控制台给予 19999 营业额，等待时间结束，主机胜利、客机失败。这是用户运行时实测，控制台设置不等同于正常经营收入。

已进一步核对现有 4.4.0e 原生反编译材料：state 4 先清场结账，随后比较目标，停在失败等待 5 或成功剧情等待 6。原补丁却在 state 4 执行前广播金额，客机据此判定，遗漏了主机本次清场收入。

当前修复将第一阶段广播移至该次 MoveNext 的 Postfix；原版未执行或未完成该段时不广播。客机继续等待并回填主机最终营业额，其他阶段广播时机不变。Release 编译通过，离线协议检查 38 项通过（含新增 8 项）。用户随后反馈修复测试通过，验证范围为上述双端复现场景，不代表完整挑战流程均已验证。

下文保留首次日志核验时的证据与不确定项。

## 结论

优先处理第一阶段结束后的主客机分歧：主机继续选材，客机未进入同轮选材，其中一份日志明确记录客机返回主菜单并断线。这不符合主机统一阶段结果的设计。现有证据不能证明游戏进程崩溃，也不能证明主机已经完成整场挑战。

最值得复现的是：**阶段消息携带清场前营业额，主机随后清场入账，客机可能在这些收入到达或应用前就判了失败。** 两组日志均符合这条时序，但缺少各端实际判定时的营业额、目标值和失败入口记录，根因仍待实测确认。

## 哪些是设计，哪些是问题

| 反馈 | 分类 | 依据与边界 |
| --- | --- | --- |
| 一部分玩家继续，另一部分进入失败结局 | 高优先级疑似同步缺陷 | 设计要求按主机依据判定。日志支持阶段后分歧，但失败剧情的具体名称及进入条件未记录 |
| 退回主菜单后断线，剩余玩家像单机 | 断线行为符合现有代码；异常入口另查 | `MpManager.OnSceneTransit` 在进入主菜单时主动断线。不能用这项设计解释此前为何分流 |
| 客机没有“某玩家已准备”提示 | 通知遗漏，低优先级 | `PrepReadyAction` 的挑战分支提前返回，未调用普通准备分支的聊天提示。不能据此判定按钮缺失 |
| 开始挑战时建议断线 | 提示过宽，低优先级 | `UniversalGameManagerPatch.LoadScene_Prefix` 只按白天直入营业场景提示，不主动断线，也未排除已支持的幽幽子试炼 |
| 使用作弊后发生分歧 | 尚不能归因 | 第二组记录立即完食、耐心不减、热火朝天、投掷上菜；记录不足以完整还原菜单开关，不能证明永久粉评开启或关闭 |
| 玩家1进入“好结局” | 表述待澄清 | 已有日志只能确认主机进入第二轮准备，不能写成整场挑战通关 |

## 根因候选与源码依据

1. `YuyukoGuestSync.Challenge.BeforeMainStep` 在 state 4 执行原版前发送营业额快照；客机回填快照后直接放行原版。
2. 主机日志随后出现 `RepellInternal` 和新增收入。现有逆向仓库的主循环原生反编译材料也显示，第一阶段恢复段先处理顾客，再比较目标；还原 C# 对这段清理过程有省略。该原生材料不能替代对测试用 4.4.0e 判定现场的核对。
3. `NightSceneEventManagerPatch.FundEdit_Prefix` 抑制客机本地入账；客机依赖单独的 `FundEditAction`。阶段包和收入包按顺序到达，不代表游戏协程会等到收入全部应用才判定。
4. `FundEditAction` 还带有 `DiscardOnStory`。若客机已经进入剧情，后续收入存在被丢弃的条件；仅凭 Received 日志不能确认业务执行成功。

因此应优先核验“清场入账前后是否跨过实际目标”。不要先改断线处理，也不要把之前三阶段吞厨具的问题套到这次第一阶段分歧上。

源码入口（相对 `src/MetaMystia.Mod/`）：`Managers/YuyukoGuestSync.Challenge.cs`、`Patches/NightScene/YuyukoMainLoopPatch.cs`、`Patches/NightScene/NightSceneEventManagerPatch.cs`、`Network/Actions/WorkScene/FundEditAction.cs`、`Patches/NightScene/YuyukoBossDataPatch.cs`、`Managers/MpManager.cs`。

## 整理后的复现步骤

这是待重放的步骤，不是本轮已经复现成功的记录。

1. 使用相同游戏版本、Mod 文件和资源配置启动三端，记录房主与 UID；保留可重放的挑战前存档。按日志优先选择最终试炼入口。
2. 三端分别完成开场对话、选择配置并点击准备；确认三端均进入第一阶段。此后只操作一端上菜，另两端不参与经营；阶段结束后仍分别推进必要对话，避免把未读完对话误判为卡住。
3. 第一轮先关闭主动作弊。围绕界面实际目标，让倒计时结束前营业额略低于目标，并保留能够在清场时结账的顾客；确认清场收入是否足以跨过目标。
4. 记录三端在第一阶段结束时的阶段消息、清场前后营业额、目标值、实际成功／失败入口、第二轮面板及连接状态。出现分歧即停止上菜、保留三端日志，不继续推完整场挑战。
5. 对照一轮“结束前已明确达标”和一轮“清场后仍未达标”，分别应全部继续、全部失败。必要时才单独加入朋友提到的辅助功能，区分是否只改变收入时机。

验收条件：三端对同一阶段给出一致结果；成功者均能进入第二轮准备，失败者均走失败收尾。剧情速度可以不同，最终分支不能不同。

仍缺证据：朋友口中的玩家编号映射、测试 DLL 身份、判定瞬间数值、两客机失败剧情画面。现有日志无需补全这些信息即可确定下一次优先核验的阶段，但不足以宣布根因或修复已验证。
