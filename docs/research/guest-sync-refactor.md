# 顾客同步重构调研

基线：`07c29c3`，目标游戏 4.4.0e；原版依据为 4.3.0c 逆向导出。仅源码审计，没有游戏实测。编号 1–9 沿用[顾客同步审计](guest-fsm-audit.md)，符卡相关问题见[符卡联机适配](spell-multiplayer.md)，本文不重复。

重构目标：结构清晰，便于接入更多 Boss 战和符卡。约束：玩家操作本地立即生效并上报主机，不等待主机回复；回撤从简，可以不做。协议不考虑跨版本兼容。

## 现状

主机运行原版顾客逻辑，在生命周期节点由 Hook 调用 `GuestFSM.On*` 广播；客机用 Prefix 跳过自主决定，收到消息后放入该顾客的等待队列，由 `Do*` 重放。上菜由双方发起、主机裁定。幽幽子本体另有手动轨道（`YuyukoGuestSync`），自带会话、订单序号和订单版本。

| 环节 | 主机探测 | 消息 | 客机落地 |
|---|---|---|---|
| 生成 | `PostInitializeGuestGroup` Prefix | `GuestSpawn` | 手写重放构造与 `PostInitializeGuestGroup`，`TrySendToSeat` 被短路 |
| 入座 | `MoveToDesk` Prefix；出队由劫持的 `CheckAndSendFromQueue` 补发 | `MoveToDesk`、`SendFromQueue` | 手写 `ReplayTrySendToSeat`，出队收尾另行执行 |
| 排队 | `MoveToQueue` Postfix | `MoveToQueue` | 手写入队，耐心回调为空 |
| 点单 | `GenerateOrderInternal` Postfix | `GenerateOrder`（含资金、剩余点单数） | `PendingOrder` 暂存后调用原版，内层 Prefix 回填 |
| 上菜 | 面板 `Send`、`Cancel`、`OnPanelClose` | `ServeSellable`、`ConfirmServe` | 主机按菜品内容裁定后广播，回声按 `ActorUid` 过滤 |
| 评价 | `TryOverrideEvaluateByBuff` Postfix | `EvaluateOrder` | 写入菜酒，以 `OverrideEvalResult` 重放 `EvaluateOrder` |
| 离场 | `LeaveFromDesk`、`PatientDepletedLeave`、队列耐心闭包、`RepellInternal` | `GuestLeave`、`PatientDepletedDesk`、`PatientDepletedQueue`、`GuestRepell` | `Bypass` 放行原版入口，或手写最小清理 |
| 异常 | 任一端状态不符或等待超时 | `GuestKill`（仅主机发） | 强制清理并移出映射 |

审计第 1 项已由 `2841bc5` 修复（客机放行完整 `PatientDepletedLeave`）。

## 问题归因

| 编号 | 根因 | 表现 | 依据 |
|---|---|---|---|
| R1 | 顾客映射没有生命周期 | `GuestsMap` 为静态表，只有 `Kill` 和幽幽子重置会移除；正常离场、跨夜、退房都不清理（第 8 项）。按控制器查找每次线性扫描两遍全表。等待队列每帧在所有场景执行，只检查连接身份，不检查场景 | 源码推断 |
| R2 | 等待队列在 Hook 内同步排空 | `To()` 立即 `Drain()`，排队操作在原版方法中途执行。第 3 项即此：`GenerateOrderInternal` Postfix 推进到 `WaitingServe` 时新订单尚未 `PushToOrder`，`OrderSeq`（取 `AllOrdersCount`）仍是旧值，旧的空确认被当作当前订单 | 源码推断 |
| R3 | 订单身份隐式 | 普通顾客用 `AllOrdersCount` 作序号，它在原版方法内变化；首单另用 `IsFirstOrder`。幽幽子本体已用显式序号 | 已核对 |
| R4 | 状态不符即销毁，两端都如此 | 主机 Hook 在意外时序触发（符卡、未知路径）时 `Kill`，强制清理原版仍在运行的顾客并广播。客机超时同样销毁本地副本，主机不知情 | 已核对 |
| R5 | 手写重放与原版分叉 | 稀客生成不计 `AddServedGuest` 与图鉴到店，`OnLeaveCallback` 置空；`tryToJumpQueue`、自定义后处理不同步；出队拆成两条消息（第 2 项） | 已核对 |
| R6 | 等待条件靠 Hook 顺序推断 | `PostEvaluation` 返回即进入 `ContinueDecision`，此时吃饭计时仍在进行（第 6 项）。评价延迟、QTE 时长等受本地修正影响，两端速度不同时等待逐单累积 | 源码推断 |
| R7 | 每顾客队列丢失跨顾客顺序 | 主机先 A 离桌、后 B 入座；客机 A 的离场若排在 A 的阻塞项之后，B 因桌位未释放一并等待，直到 A 超时被销毁 | 源码推断 |
| R8 | 生命周期缺少通道 | 生成出口 1、4：主机静默 `MoveToSpawn`，两端状态停在 `Constructed`，客机无等待项、永不超时（第 4 项；不阻塞打烊）。排队客经打烊、快进、符卡离开时不发消息，状态停在 `Queued`，打烊时各端自清。伙伴不同步：客机伙伴写本地订单、消耗本地库存，`EvaluateOrder` 被跳过 | 已核对；伙伴后果为源码推断 |
| R9 | 数值各端各算 | 心情初值 = 本地玩家等级加成 + 本地随机，两端系统性不同，只有赶客同步主机值（第 9 项）；心情影响客机耐心上限、心情条和符卡的心情归零驱逐。连击只在赶客时同步。评价结果取自彩蛋和改判回调之前（第 7 项） | 已核对 |
| R10 | 剧情期间同步整体失效 | `ShouldSkipAction` 含 `InStory`：剧情中该端所有顾客 Hook 走原版，主机不广播、客机本地生成；顾客消息 `DiscardOnStory` 被丢弃 | 条件已核对；营业中途是否播放 timeline 待验证 |
| R11 | 上菜预测没有归属 | 冲突按菜品内容比较，同样两份菜无法区分；被替换的物品退回库存或保温箱而非原托盘。外部关闭面板只发空确认，其他端保留旧的待上菜显示和预填 | 源码推断 |
| R12 | 判断散落 | 顾客 Patch 中 `ShouldSkipAction \|\| !HasRoomPeers` 29 处，`IsBody`、`IsReimuProtectionGuest`、`IsManualGuest` 27 处；不可达分支抛异常；查找返回 null 时多处直接解引用（如客机 `EvaluateOrder_Prefix`）；灵梦保护仍用 `PatchBypassToken` | 已核对；空引用触发条件为源码推断 |
| R13 | 玩家操作等待主机 | 客机赶客只发请求，主机结果到达前顾客不动；客机上齐菜后本地评价被跳过，等主机评价消息；补菜恢复耐心（`FinishOrderStatus` → `AddPatient`）只在上菜端执行，不上报，主机仍按原耐心判定 | 已核对 |
| R14 | 主机排队客机请求，拒绝无回执 | 主机把客机上菜、确认放入等待队列（第 3 项的另一半）；拒绝时不通知，若之后没有相关广播，客机本地订单与主机长期不一致，物品已从托盘扣除 | 源码推断 |
| R15 | 断线后顾客卡住 | 客机断线后留在夜间按单机继续。重放入座省略了首单计时，续单入口被跳过；等首单和等续单的顾客既不点单也不离开，打烊等待无法结束。断线时只有幽幽子本体交还原版 | 源码推断 |
| R16 | 点单人不同步 | 主机每单随机选点单人（`PostGenerateOrder`），评价喜好标签取自该人；客机订单记在第一位顾客名下，喜好标签用构造时的随机人选。评价被主机覆盖，目前只影响显示；客机本地先行评价时必须同步 | 已核对 |

其他：

- 金钱经 `FundEdit`、`TipEdit` 等按金额同步，不带顾客标识；接收端按本地 `ExtraFundModifier` 缩放。托盘个人所有，不同步。
- 超出忍耐的稀客：客机跟随主机结果进入同一分支，也执行本地的 `TriggerNegativeBuff`，两端各一次、随机独立；离场 `triggerLeaveBuff` 透传，客机也触发本地离场卡。
- [#145](https://github.com/MetaMystia/MetaMystia/issues/145) 为原版缺陷：`WorkSceneServePannel.OnExitExtern` 两次调用 `ReturnPass`，后者固定退回 `willServeFood`，第二次退回空值，酒水丢失。逆向注释称二进制如此，4.4.0e 待核对。
- 逆向中 `EventManager.HasCreatorBoxCoroutineEnd` 为 `onCreatorBoxGuestInstantiateLoop == null`，按字面普通营业会让所有顾客从出口 1 离场，与实际不符，还原有误；客机置空该字段的影响待核对。

## 目标结构

### 同步分类

| 类别 | 归属 | 客机 | 主机 | 冲突与回撤 |
|---|---|---|---|---|
| 玩家操作：上菜、确认、补菜、赶客、符卡触发 | 操作者 | 本地立即执行原版并上报结果 | 立即应用或丢弃，不排队；先到先得，结果发给其他人，丢弃时回执操作者 | 被拒的物品退回操作者托盘；其余差异由后续广播或快照覆盖，表现不回撤 |
| 世界事件：生成、入座、排队、点单、评价结果、离场 | 主机 | 立即应用；本地动画落后时追上，不等待 | 在原版收口处探测并广播 | — |
| 数值：心情、资金、剩余点单数、耐心；连击与断连击计数 | 主机 | 直接覆盖 | 变化时标记，每帧合并发送 | 覆盖 |
| 表现：台词、音效、动画 | 各端 | 本地 | 本地 | 不同步 |

操作者本地先行评价时，主机评价结果到达后只覆盖数值与后续流程；原版 `HasEvaluated` 阻止同一单重复评价。其他端照旧按主机结果重放。

### 收口

- 主机在原版收口处探测，不按来源（玩家、符卡、事件、打烊）分别写消息：生成 `PostInitializeGuestGroup`，入座 `TrySendToSeat`，点单 `GenerateOrderSession`，评价最终结果，离桌 `LeaveFromDesk`，未入座离开 `MoveToSpawn`、`FlyToSpawn`。后两者在原版只有 `GuestsManager` 的 11 处和 `Spell_Yuuka` 的 2 处调用，统一覆盖生成出口 1/4、排队耐心耗尽、打烊清队列、未入座驱逐。
- 客机在同一组收口只放行重放、本地轨道和本人操作；符卡、事件在客机上的本地调用被截住，结果等主机广播。
- 符卡适配因此只处理分支决定；对顾客生命周期和数值的影响由收口与快照同步，不逐卡写顾客消息。

### 客机落后

不再超时销毁，按原因处理：

| 情况 | 处理 |
|---|---|
| 本地动画或计时未到（入座途中、吃饭中） | 宽限约 1–2 秒游戏时间等自然完成；到期直接追上：补做到座登记或结束吃饭，再应用主机事件 |
| 桌位仍被本地旧顾客占用 | 以主机为准，先按离场清理旧顾客，再入座 |
| 本地没有该顾客或缺前置事件（剧情期间被丢弃等） | 向主机请求该顾客快照：生成参数、阶段、桌位、当前订单与已上菜、数值；在对应阶段直接生成 |
| 主机已判定离开 | 越过等待项，按本地状态清理 |

快照请求同时可用于剧情结束后补齐，以及将来的中途加入。

### 组成

| 部分 | 内容 |
|---|---|
| 登记表 | `Scopes.Scene` 内的状态：`RuntimeId` 与控制器地址双索引、轨道、每帧 Tick；作用域结束整体失效，断线（`resume`）时把顾客交还原版，取代静态 `GuestsMap` |
| 顾客记录 | 原 `GuestFSM` 的状态、订单序号、点单人、就绪条件（已到座、已吃完）、宽限中的事件；不含 On/Do 方法 |
| 通道 | 每条消息一个文件，含主机发送、客机应用和接受的源状态；原 On/Do 成对方法移入对应消息 |
| 数值快照 | 顾客与房间两张脏表，每帧合并为一条消息 |
| 脚本顾客 | 从 `YuyukoGuestSync` 提取通用部分：绑定剧情创建的实体、手动订单序号、评价最终结果、本地回调与主机完成的汇合。各 Boss 只保留阶段、吞厨具、血量等专属逻辑 |
| Hook | 仍在各游戏类 Patch 中，开头统一取模式：单机、本地轨道、主机、客机 |

轨道：复制（普通、稀客）、脚本（Boss 本体）、本地（灵梦保护、路人）。

## 分步实施

| 步骤 | 内容 | 风险 |
|---|---|---|
| G1 登记表 | 场景作用域、双索引、轨道、统一模式判断；断线交还原版；`PluginHost`、调试命令、幽幽子绑定改用登记表；联机禁用伙伴 | 低 |
| G2 主机不排队、客机不等 | 安全点排空；主机对客机请求立即应用或丢弃并回执；主机不再销毁；离场越过队列；宽限后追上；吃完改在 `MainOrderCycle` 入口标记 | 中 |
| G3 收口与快照 | 客机收口规则；合并入座、离场（含 `MoveToSpawn` 探测）；显式订单序号与点单人；数值快照；评价最终结果 | 中 |
| G4 玩家操作先行 | 赶客、评价、补菜耐心本地先行并上报；上菜槽位版本、被拒退回托盘、外部关闭撤回；#145 单独修 | 高 |
| G5 修复与接入 | 顾客快照请求；提取脚本顾客并迁移幽幽子本体；符卡按分支决定接入 | 中 |

登记表、事件应用结果、追赶判定、槽位版本不依赖游戏对象，可按 Flow 测试的方式链接源码、以地址作键离线测试。实测用例另补：出队入座、桌上与队列耐心耗尽、双端赶客、打烊时有排队、两人同时上菜、放入后外部关闭面板、补菜后耐心、客机断线后打烊、连续两夜。

## 待决

- 客机先行赶客而主机原版条件不成立（护盾、本地 buff 不同）时：主机以操作者结果为准强制执行，或忽略（该顾客在操作者处已离开）。
- 剧情：先核实营业中途是否播放 timeline；若会，客机缓存顾客消息，或丢弃后用快照补齐。
- 消息合并（16 类减至约 10 类），或保留类型只加共同基类。
- 客机的个人进度副作用（稀客到店记录、接待计数、委托完成、小费成就）归谁，与符卡的个人归属一并决定。
- 代码位置：新建 `Multiplayer/Guests/`，或留在 `Managers/`。
