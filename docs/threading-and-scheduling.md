# 线程与调度规范

## 线程边界

- Unity 主线程负责生命周期、场景、UI 和游戏对象。
- `TcpConnection` 的异步 IO 负责读写网络帧和投递传输事件。
- `EndpointHost.Pump()` 顺序执行端点状态机；Mod 在主线程调用，独立服务器在自己的主循环调用。
- `Task` 用于网络、文件等 IO；协程用于主线程的延迟、等待和周期逻辑。

后台线程不得访问 Unity 或游戏对象，只能处理已确认线程安全的纯托管数据。不要阻塞 Unity 主线程，不使用 `.Result`、`.Wait()` 或 `Thread.Sleep` 等待网络和游戏状态。

## 网络状态的应用

`MpWire.FlushInbox()` 在主线程按顺序处理连接结果、会话确认、载荷和断开事件。连接回调带 Attempt，房间操作带绑定与阶段，过期结果不得修改新状态。

IO 线程不执行 Action，不修改玩家、成员、场景或 UI。游戏载荷在主线程解码，数据进入 Store，实际效果通过 RoomGameplay 的当前阶段处理。

## 切回主线程

```csharp
PluginManager.RunOnMainThread(() =>
{
    // 访问当前仍有效的游戏对象
});
```

`PluginManager` 的队列由 `PluginHost.Update()` 每帧处理。

- 后台只准备普通数据，进入主线程后再读取游戏对象。
- 不长期捕获生命周期不明的游戏对象。
- 房间相关回调检查捕获的绑定及阶段；仅仅切回主线程不能保证旧操作仍有效。
- `OnMainThread` 属性表达约束，不会自动切换线程。

## 等待与协程

新增等待逻辑优先使用协程，参见 [协程规范](coroutine-style.md)。房间业务使用 `RoomGameplay.Run()` 登记句柄，退出或换阶段时统一停止。

网络效果等待队列由 RoomGameplay 统一管理；不要给每个 Handler 再建一套转场缓存。超时记录原因并结束当前玩法绑定，不能无限等待或把未处理操作视为成功。

`CommandScheduler` 计划弃用，仅维护必要的既有调用，不新增接口或包装层。时序不明确时先读游戏源码，不能靠调度器掩盖未知行为。

## 异步与 IO

网络、HTTP、文件操作允许 `async` 和 `try-catch`；游戏状态和普通业务逻辑不以异常捕获掩盖错误。

禁止 `async void`，除非框架签名要求。IO 完成后只投递结果，不在主线程重做 IO。独立服务器的循环等待不受 Unity 主线程限制。
